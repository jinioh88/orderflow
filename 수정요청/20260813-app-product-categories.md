# 카테고리 목록 조회 API 신설 요청 (카테고리 칩 UI용)

- status: 완료
- 요청 세션: app
- 요청일: 2026-08-13
- 대상 API: 신규 (`GET /products/categories` 제안)
- 관련 스토리: US-CAT-01 (카테고리 탐색), US-ORD-01 (발주 카탈로그 탐색)

## 현재 스펙

없음. CAT 에픽(3장)에 카테고리를 **목록으로 조회하는** 엔드포인트가 없다.
`GET /products`(3.2.2)에 `category` 쿼리(정확 일치 필터)만 있고, 상품 객체(3.1)의
`category`는 자유 문자열이다 (계층 카테고리 미도입 — erd 3.2).

## 요청 내용

테넌트 내에서 **실제로 사용 중인 카테고리 목록**을 반환하는 조회 API를 요청한다.

```
GET /products/categories
접근: 테넌트 소속 전체 (STORE_OWNER 포함 — GET /products와 동일)
```

응답 `200` (공통 래퍼 1.3, 페이징 없음):

```json
{ "data": ["냉동식품", "소스류", "포장재"] }
```

- 정렬은 가나다순(또는 서버가 정하는 안정적 순서) 고정이면 충분하다.
- 상품 수 같은 부가 정보는 필요 없다. 필요해지면 그때 다시 요청하겠다.
- `status=SUSPENDED`인 상품만 가진 카테고리를 포함할지는 서버 판단에 맡긴다.
  앱은 `ON_SALE`만 조회하므로(아래 사유 참조) **판매중 상품이 있는 카테고리만** 오는 편이
  칩을 눌렀는데 빈 목록이 나오는 상황을 막아 준다.

## 사유

디자인 시스템 `04-app-components §3.1`이 카탈로그 탐색 UI로 **카테고리 칩(가로 스크롤 1행,
"전체"가 항상 첫 번째)** 을 규정하는데, 칩에 무엇을 그릴지 알아낼 방법이 계약에 없다.

앱에서 가능한 대안은 둘 다 결함이 있다:

1. **로드된 페이지에서 추출** — 스크롤을 내릴수록 칩이 늘어나고, 첫 페이지에 없는 카테고리는
   아예 보이지 않는다. 칩이 "탐색 수단"이 아니라 "이미 본 것의 요약"이 되어 버린다.
2. **전체 상품 1회 조회 후 수집** — 정확하지만 상품이 많은 테넌트에서 진입이 느려진다.
   "영업 마감 후 5분 안에 발주"라는 앱 목표(app/CLAUDE.md)와 정면으로 충돌한다.

카테고리는 M2 발주 화면(US-ORD-01)에서도 같은 UI로 재사용되므로, 지금 계약에 넣어 두는 편이
나중에 발주 화면을 다시 고치는 것보다 싸다.

## 진행 상황 (앱 세션)

공통 규칙 10에 따라 이 요청으로 작업을 멈추지 않는다. **M1 카탈로그는 검색·목록·무한 스크롤까지
먼저 구현**하고, 카테고리 칩 태스크만 이 요청 처리 시점까지 보류한다 (사용자 결정 2026-08-13).

## 처리 결과 (서버 세션 기록)

- 승인: 사용자, 2026-08-13
- 반영일: 2026-08-13
- 스펙 위치: `server/docs/api/03-cat.md` **3.2.11** + `api-spec.md` 엔드포인트 인덱스

### 반영 내용 — 요청대로 신설

```
GET /api/v1/products/categories
접근: HQ_ADMIN, HQ_MANAGER, STORE_OWNER (GET /products와 동일)
응답 200: { "data": ["부자재", "원재료"] }   ← 로컬 서버 실제 응답
```

요청서의 제안을 그대로 채택했다 — 경로·응답 형태·페이징 없음·부가 정보 없음 모두 동일하다.

**절 번호가 3.2.9가 아니라 3.2.11인 점만 유의**해 달라. 3.2.9·3.2.10은 CAT 접근 매트릭스에서
엑셀 엔드포인트에 이미 배정돼 있어(상세는 3.3.2·3.3.3) 재번호 부여 없이 뒤에 붙였다.

### 판단이 필요했던 항목 — 서버 결정

**`SUSPENDED`만 있는 카테고리는 제외한다** (요청서가 서버 판단에 맡긴 항목).
요청서의 선호("판매중 상품이 있는 카테고리만")를 그대로 채택했다 — 칩을 눌렀는데 빈 목록이
나오는 상황을 막는 것이 맞다고 봤다. 즉 `status = ON_SALE`인 상품이 하나라도 있는 카테고리만 온다.

> 나중에 웹 본사 관리자 화면이 같은 API로 칩을 그린다면, 판매중지 상품만 남은 카테고리가
> 칩에서 사라져 그 상품들에 칩으로 접근할 수 없게 된다. 그때는 `status` 쿼리 파라미터를
> **기본값 ON_SALE**로 추가하면 되고, 그 경우에도 **앱은 무변경**이다.

### 정렬·중복

카테고리명 오름차순 고정, 중복 제거. 상품이 없으면 `404`가 아니라 `{ "data": [] }`.

### 성능

`product` 테이블에 인덱스를 추가하지 않았다. `tenant_id` 선두 유니크 인덱스로 범위 스캔 후
중복 제거가 되며 MVP 규모(테넌트당 수천 건)에서는 충분하다고 판단했다. 느려지면
`(tenant_id, status, category)` 커버링 인덱스를 추가한다 (erd.md·schema.sql 동반 갱신 필요).

### 앱 세션에 알림 — 카테고리 문자열은 정규화되지 않는다

`category`는 자유 문자열이고 **등록 시 trim·대소문자 정규화를 하지 않는다.**
따라서 `"소스류"`와 `"소스류 "`(끝 공백)는 **별개 칩 2개로 반환된다.** 특히 엑셀 업로드(3.3.2)로
대량 등록할 때 현실화되기 쉽다. 이번 요청 범위 밖이라 손대지 않았고 서버 백로그
발견 항목으로 올려 뒀다 — 기존 데이터 마이그레이션이 얽혀 조용히 끼워 넣을 사안이 아니다.
앱에서 칩이 중복으로 보이면 이 원인일 수 있다.
