# 카테고리 목록 조회 API 신설 요청 (카테고리 칩 UI용)

- status: 요청됨
- 요청 세션: app
- 요청일: 2026-08-13
- 대상 API: 신규 (`GET /products/categories` 제안)
- 관련 스토리: US-CAT-01 (카테고리 탐색), US-ORD-01 (발주 카탈로그 탐색)

## 현재 스펙

없음. CAT 에픽(3장)에 카테고리를 **목록으로 조회하는** 엔드포인트가 없다.
`GET /products`(3.2.2)에 `category` 쿼리(정확 일치 필터)만 있고, 상품 객체(3.1)의
`category`는 자유 문자열이다 (계층 카테고리 미도입 — erd 3.2).

## 요청 내용

테넌트 내에서 **실제로 사용 중인 카테고리 목록**을 반환하는 조회 API를 요청한다.

```
GET /products/categories
접근: 테넌트 소속 전체 (STORE_OWNER 포함 — GET /products와 동일)
```

응답 `200` (공통 래퍼 1.3, 페이징 없음):

```json
{ "data": ["냉동식품", "소스류", "포장재"] }
```

- 정렬은 가나다순(또는 서버가 정하는 안정적 순서) 고정이면 충분하다.
- 상품 수 같은 부가 정보는 필요 없다. 필요해지면 그때 다시 요청하겠다.
- `status=SUSPENDED`인 상품만 가진 카테고리를 포함할지는 서버 판단에 맡긴다.
  앱은 `ON_SALE`만 조회하므로(아래 사유 참조) **판매중 상품이 있는 카테고리만** 오는 편이
  칩을 눌렀는데 빈 목록이 나오는 상황을 막아 준다.

## 사유

디자인 시스템 `04-app-components §3.1`이 카탈로그 탐색 UI로 **카테고리 칩(가로 스크롤 1행,
"전체"가 항상 첫 번째)** 을 규정하는데, 칩에 무엇을 그릴지 알아낼 방법이 계약에 없다.

앱에서 가능한 대안은 둘 다 결함이 있다:

1. **로드된 페이지에서 추출** — 스크롤을 내릴수록 칩이 늘어나고, 첫 페이지에 없는 카테고리는
   아예 보이지 않는다. 칩이 "탐색 수단"이 아니라 "이미 본 것의 요약"이 되어 버린다.
2. **전체 상품 1회 조회 후 수집** — 정확하지만 상품이 많은 테넌트에서 진입이 느려진다.
   "영업 마감 후 5분 안에 발주"라는 앱 목표(app/CLAUDE.md)와 정면으로 충돌한다.

카테고리는 M2 발주 화면(US-ORD-01)에서도 같은 UI로 재사용되므로, 지금 계약에 넣어 두는 편이
나중에 발주 화면을 다시 고치는 것보다 싸다.

## 진행 상황 (앱 세션)

공통 규칙 10에 따라 이 요청으로 작업을 멈추지 않는다. **M1 카탈로그는 검색·목록·무한 스크롤까지
먼저 구현**하고, 카테고리 칩 태스크만 이 요청 처리 시점까지 보류한다 (사용자 결정 2026-08-13).
